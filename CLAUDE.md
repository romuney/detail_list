# CLAUDE.md

«Детальные списки» HR Executive (дашборд 7241 в Proteus — корпоративном BI, форке
Superset): два быстрых чарта без нативных фильтров — **«Детальные списки»** и
**«Детальные списки КП»**, две вкладки с одинаковой вёрсткой. Фильтры — внутри
кастомного чарта `react_sanbbox`, у чарта свой датасет, открытие — 5 000 сотрудников и две
колонки. Боевые системы (ClickHouse, Proteus) отсюда недоступны: владелец вставляет файлы
руками по инструкции из папки поставки.

Разбор, схема, замеры и что собрано — **`docs/analysis.md`** (читать первым; раздел 9 —
реализация и отличия от плана).

## Стенд (без доступа к бою)

chdb 2.1.1 (= ClickHouse 24.8, как в бою) — в отдельном venv (`pip install chdb==2.1.1
jinja2 pyyaml`); Jinja датасета рендерится, как в Proteus (`filter_values`,
`current_username`, AlwaysTrue при сохранении). В chdb нет `base64Encode` — строки
кодирует стенд.

```
<venv>/bin/python stand/world.py              # синтетический мир → stand/.db: 100 тыс. сотрудников, 200 тыс. аллокаций КП, warden
<venv>/bin/python stand/check.py [us|kp]      # 292 проверки: сверка с прежним датасетом выгрузки, независимый расчёт, режимы ClickHouse
<venv>/bin/python stand/live.py               # чарт в браузере: ?user=a.user|hr.super|p.lead|nobody, ?mode=us|kp, ?w=, ?selfoff=1
NODE_PATH=$(npm root -g) node stand/click.cjs # живой прогон: каждый контрол обоих чартов (58 шагов, 0 провалов)
node $(npm root -g)/eslint/bin/eslint.js -c stand/eslint.chart.cjs --no-config-lookup proteus/detail-list.chart.js
<venv>/bin/python stand/mock.py               # proteus/detail-list.mock.json для smoke скилла (live.py остановить: chdb держит каталог)
python3 stand/pack.py [--check]               # файлы 1–4 поставки из исходников
```

Логины мира: `a.user` — частичный доступ (маски warden), `hr.super` — всё, `p.lead` — лидер
профессии, `an.a.sokolova` — правило логина CROSS-8440, `nobody` — нет строки в warden.

## Инварианты — не ломать

- **Сначала отобрать, потом упаковать:** id сотрудников — `ORDER BY … LIMIT` по
  отфильтрованной таблице; маски warden, чистка и упаковка — только для них и только по
  видимым колонкам. Итог — `countIf` в meta.
- **Один исходник на два чарта:** SQL отличается строкой `MODE`, JS — строкой `ns`
  (`dl` / `dlk`); файлы поставки собирает `stand/pack.py`. Режим чарт берёт из meta.
- **Контракт датасета:** 5 колонок `role k v n j`, роли meta / f / fq / t / q / s / r (форматы —
  шапка SQL). Новая колонка = правка «Измерений» владельцем (`proteus/FIELDS.md`).
- **Части ответа (`pt`):** без носителя — meta и строки; значения фильтров и деревья —
  когда их открывают; поиск и дети узла — одни находки. Чарт держит части в
  `state.cache` по подписи фильтров и один раз досылает строки, если их нет.
- **Носители:** основа + суффикс чарта (`_f` / `_kf`, в meta — `cf`), в SELECT не
  выводятся, `value = []` не эмитится; метка `rq` снимает ожидание; кросс-фильтр каждого
  чарта — только на себя (JSON-метаданные дашборда, инструкция поставки п. 4).
- **Размер запроса:** списки фильтров — константами `WITH` (`x IN кортеж` — множество), а
  не литералом в каждом условии: худший случай (2 000 логинов + 500 значений) — 194 КБ
  при `max_query_size` 256 КБ, проверка в `check.py`. `ARRAY JOIN` по алиасу `WITH` старый
  анализатор 24.8 не принимает.
- **Доступ:** warden по `current_username()` — логика прежнего датасета слово в слово (не
  слабее текущей); скрытое — `'⛔'`, в «Копировать» — прежний текст. Нет строки в warden —
  только meta (`ok = 0`).
- **Деревья:** до 1 500 узлов — целиком, больше — верхние 3 уровня, путь и дети выбранного,
  глубже — дети узла по раскрытию и поиск. УС и ЮС — по rk уровней (УС с 3-го), КП — по
  пути имён (id — 12 знаков md5 пути, фильтр — сам путь через `\x1F`).
- **КП:** строка на аллокацию — только при колонке аллокации или уровня КП; поля
  сотрудника, кроме MasterID, — только в первой строке блока (чарт берёт их оттуда).
- **Без вспомогательных датасетов:** значения фильтров, деревья и поиск — из самой таблицы
  списка; `cross_filter_*_structure` и датасеты нативных фильтров не используются.
- **ClickHouse 24.8:** без SETTINGS в датасете, `ifNull` на каждом выходе, проверка старым
  и новым анализатором, `prefer_column_name_to_alias`, `join_use_nulls`, `group_by_use_nulls`.
- **Чарт:** ES5, БЛОКИ 1–7 шаблона скилла, состояние в `window.__pvtState[ns]`, классы с
  префиксом ns; base64 — `atob` + `TextDecoder`; поле ввода при поиске не пересоздаётся
  (точечные обновления списка и таблицы); вид — профиль Proteus Adoption, как HRBP HUB
  (кегли ролями `CFG.fonts`, веса 400 / 500 / 600, контролы 34 px).
- **По умолчанию:** 2 колонки (MasterID + дата найма), 5 000 сотрудников, сортировка
  MasterID; «Загружать» — 5 000 / 10 000 / 25 000; лимит строк чарта в Proteus — 50 000.
- Скратч (пробный SQL, скриншоты, журнал `check.py` скилла) в репозиторий не кладём —
  только живые инструменты `stand/` и выводы в `docs/`.

## Что не проверено стендом

Боевые объёмы и время ClickHouse-кластера, размер деревьев УС / КП в бою, DOM борда для
CSS (файл 5 поставки), поведение Proteus с двумя такими чартами на соседних вкладках.
