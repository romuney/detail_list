# CLAUDE.md

«Детальные списки» HR Executive (дашборд 7241 в Proteus — корпоративном BI, форке
Superset) без нативных фильтров: две вкладки одного борда — **«Детальные списки»** и
**«Детальные списки КП»**, на каждой два кастомных чарта `react_sanbbox`: **строка фильтров**
(два компактных ряда, все значения и деревья уже в ответе, широкая выпадашка поверх списка —
разворот iframe) и **список** (5 000 сотрудников, колонки по запросу, открытие — две). Четыре
датасета из одного SQL. Боевые системы (ClickHouse, Proteus) отсюда недоступны: владелец
вставляет файлы руками по инструкции из папки поставки.

Разбор, схема, замеры и что собрано — **`docs/analysis.md`** (читать первым; раздел 9 —
реализация и отличия от плана).

## Стенд (без доступа к бою)

chdb 2.1.1 (= ClickHouse 24.8, как в бою) — в отдельном venv (`pip install chdb==2.1.1
jinja2 pyyaml sqlglot==26.33.0 sqlparse`); Jinja датасета рендерится, как в Proteus
(`filter_values`, `current_username`, AlwaysTrue при сохранении). В chdb нет `base64Encode` —
строки кодирует стенд.

```
<venv>/bin/python stand/world.py              # синтетический мир → stand/.db: 100 тыс. сотрудников, 200 тыс. аллокаций КП, warden
python3 stand/parse.py                        # разбор SQL sqlglot, как Proteus при сохранении датасета (без chdb; версии 23–30 — PYTHONPATH)
<venv>/bin/python stand/check.py [us|kp]      # 339 проверок: оба вида (список, строка фильтров), сверка с прежним датасетом, независимый расчёт, режимы ClickHouse, круг sqlglot
<venv>/bin/python stand/live.py               # борд вкладки: строка фильтров + список в iframe-песочницах, области кросс-фильтров, канал скриншотов, CSS файла 9; ?user=a.user|hr.super|p.lead|nobody, ?mode=us|kp, ?w=, ?fh=, ?selfoff=flt|list
NODE_PATH=$(npm root -g) node stand/click.cjs # живой прогон борда: каждый контрол обоих чартов обеих вкладок (80 шагов, 0 провалов)
node $(npm root -g)/eslint/bin/eslint.js -c stand/eslint.chart.cjs --no-config-lookup proteus/detail-list.chart.js
<venv>/bin/python stand/mock.py               # моки smoke скилла: detail-list.mock.json и detail-list-filters.mock.json (live.py остановить: chdb держит каталог)
python3 stand/pack.py [--check]               # файлы 1–8 поставки из исходников
```

Логины мира: `a.user` — частичный доступ (маски warden), `hr.super` — всё, `p.lead` — лидер
профессии, `an.a.sokolova` — правило логина CROSS-8440, `nobody` — нет строки в warden.

## Инварианты — не ломать

- **Вкладка — два чарта, два запроса параллельно.** Строка фильтров (вид `filters`) эмитит
  фильтры себе (счётчики) и списку своей вкладки; список (вид `list`) — себе сортировку, лимит,
  колонки. Области — JSON-метаданные дашборда (инструкция поставки, п. 4). Всё, что эмитит
  строка, перезапрашивает и список — поэтому у строки нет запросов «по открытию»: значения и
  деревья приходят целиком (поиск в датасете — только если пришло не всё).
- **Сначала отобрать, потом упаковать:** id сотрудников — `ORDER BY … LIMIT` по
  отфильтрованной таблице (`sel_ids`); маски warden, чистка и упаковка — только для них и
  только по запрошенным колонкам. Строка собирается до оконной функции; у КП со строками
  аллокаций поля сотрудника — одним `ANY LEFT JOIN` на сотрудника. Итог — `countIf` в meta.
- **Колонки списка — по запросу** (носитель `cols`, по умолчанию MasterID и дата найма):
  открытие ≈0,3 с и 0,1 МБ; добавить колонки — один запрос, убрать — без запроса.
- **Один исходник:** SQL — строки `MODE` (us / kp) и `VIEW` (list / filters), 4 датасета; JS
  списка — строка `ns` (`dl` / `dlk`), строки фильтров — (`dlf` / `dlkf`); файлы поставки
  собирает `stand/pack.py`. Режим чарт берёт из meta.
- **Контракт датасета:** 5 колонок `role k v n j`. Вид list — meta / r; вид filters — meta / F
  (атрибут одной строкой, base64) / T (узлы деревьев пачками, обход в глубину: родитель —
  ближайший выше узел меньшего уровня, путь КП чарт собирает из имён) / s / q / fq (форматы —
  шапка SQL). Новая колонка = правка «Измерений» владельцем (`proteus/FIELDS.md`).
- **Носители:** основа + суффикс вкладки (`_f` / `_kf`, в meta — `cf`), в SELECT не выводятся,
  `value = []` не эмитится. Метки: `frq` — строки фильтров (эхо в обоих видах), `rq` — списка.
  «Применить» рассылает соседним iframe `DL_FLT {cf, frq}`: список показывает «Обновляю…», пока в
  его ответе нет той же `frq`.
- **Строка фильтров** (`CFG.shelf`): разделы и порядок нативных фильтров 7241, два ряда
  (`fitPills`): прячутся сначала незаданные атрибуты с конца, период / численность / список /
  структуры / заданные — на виду; остальное — «Ещё N». Выпадашка — в overlay, `position:fixed`
  (smoke видит её в overlay); при открытой выпадашке и подсказке — сигнал `ECHARTS_UPDATE_DATA_URL`
  с маркером `REwtRkxULURELU9O`, CSS файла 9 разворачивает iframe строки прозрачным слоем
  (костыль строки ЦА Proteus Adoption, `pa-ca-bar`); высота строки закреплена до сжатия iframe.
- **Размер запроса:** списки фильтров — константами `WITH` (`x IN кортеж` — множество), а
  не литералом в каждом условии: худший случай (2 000 логинов + 500 значений) — 194 КБ
  при `max_query_size` 256 КБ, проверка в `check.py`. `ARRAY JOIN` по алиасу `WITH` старый
  анализатор 24.8 не принимает.
- **Доступ:** warden по `current_username()` — логика прежнего датасета слово в слово (не
  слабее текущей); скрытое — `'⛔'`, в «Копировать» — прежний текст. Нет строки в warden —
  только meta (`ok = 0`).
- **Деревья и значения:** у атрибута — до 5 000 значений, дерево — до 40 000 узлов целиком
  (больше — верх, путь и дети выбранного, остальное — поиском `q`). УС и ЮС — по rk уровней (УС
  с 3-го), КП — по пути имён (фильтр — сам путь через `\x1F`). Счётчик — при остальных фильтрах.
- **КП:** строка на аллокацию — только при колонке аллокации или уровня КП; поля
  сотрудника, кроме MasterID, — только в первой строке блока (чарт берёт их оттуда).
- **Без справочников:** значения фильтров, деревья и поиск — из самой таблицы списка (вид
  `filters` того же SQL); `cross_filter_*_structure` и датасеты нативных фильтров не используются.
- **ClickHouse 24.8:** без SETTINGS в датасете, `ifNull` на каждом выходе, проверка старым
  и новым анализатором, `prefer_column_name_to_alias`, `join_use_nulls`, `group_by_use_nulls`.
- **Парсер Proteus (sqlglot) — до ClickHouse:** SQL датасета разбирается при сохранении
  («Некорректный SQL запрос: →…←» — так упало `GROUP BY intDiv(…) AS ch`, 29.09) и может
  перепечатываться (Superset 4.1+ форматирует SQL чарта). Поэтому: без алиасов в `GROUP BY`,
  без `\x`-экранов в строках (`'\x1F'` перепечатается как `'\\x1F'` — разделитель пути КП —
  `char(31)`, класс управляющих — `'[[:cntrl:]]'`); `\t`, `\n`, `\'`, `\\` переживают печать.
  Разбор — `stand/parse.py` (sqlglot 23–30 + «только SELECT»), перепечатанный запрос отдаёт
  тот же ответ — раздел 4 `stand/check.py`. chdb такие ошибки не ловит: он выполняет всё.
- **Чарт:** ES5, БЛОКИ 1–7 шаблона скилла, состояние в `window.__pvtState[ns]`, классы с
  префиксом ns; base64 — `atob` + `TextDecoder`; поле ввода при поиске не пересоздаётся
  (точечные обновления списка и таблицы); вид — профиль Proteus Adoption, как HRBP HUB
  (кегли ролями `CFG.fonts`, веса 400 / 500 / 600, контролы 34 px).
- **Больше 25 000 под фильтрами** — плашка «сузьте фильтры» над таблицей; от загруженного
  до 25 000 — «Загрузить всех» (`limNoteHTML`).
- **По умолчанию:** 2 колонки (MasterID + дата найма), 5 000 сотрудников,
  сортировка MasterID ↑ (у прежних датасетов ORDER BY нет — порядок случайный, повторять
  нечего); «Загружать» — 5 000 / 10 000 / 25 000; лимит строк чарта в Proteus — 50 000.
- Скратч (пробный SQL, скриншоты, журнал `check.py` скилла) в репозиторий не кладём —
  только живые инструменты `stand/` и выводы в `docs/`.

## Что не проверено стендом

Боевые объёмы и время ClickHouse-кластера, размер деревьев УС / КП в бою, разворот iframe
строки фильтров на борде 7241 (канал скриншотов и CSS — как на борде Proteus Adoption),
поведение четырёх чартов на двух вкладках одного дашборда.
