# Детальный список — разбор выгрузки и план оптимизации

Разбор YAML-выгрузки из корня репозитория (29.09) и предложение, как сделать из неё
быстрые борды без нативных фильтров: все фильтры внутри чарта, один запрос на открытие
и на «Применить», список — из памяти браузера. Реализации пока нет: ниже схема, замеры
на стенде и вопросы, без ответа на которые сборку начинать рано (раздел 8).

## 1. Что в выгрузке

Дашборд 13198 **«[Найм HQ] Анализ закрытых вакансий»**, база Proteus CROSS
(`prod_proteus`), две вкладки. Листов «детальный список по Каталогу продуктов» и «по
параллельной структуре» в выгрузке нет: Каталог продуктов и управленческая структура
здесь — только блоки фильтров по уровням (12 и 9 выпадашек).

| Вкладка | Чарты | Что показывает |
|---|---|---|
| Сводная | «Бирюза таблица» (135398, handlebars, лимит 5 000) | сводная «Разрез 1 × Разрез 2»: MTD, MTD год назад, YTD, PY, PYTD, 12 мес. и столбики 24 месяцев, строка Total. Разрез выбирается из 43 вариантов: стрим, специализация, каналы, рекрутеры, УС-2…11, КП-1…12 |
| Детализация | 5 «таплок» (год, месяц, разрез 1, разрез 2, тип HRS — таблицы по 1 000 строк), шапка «Выбранные фильтры» (handlebars), список «Детализация по закрытым» (142653) | таплки кликом фильтруют список (кросс-фильтры); список — стандартная `table` |

Список 142653: режим aggregate, 24 поля в GROUP BY и ни одной меры (дата закрытия,
ссылки HRS и Candy — HTML, собранный в SQL, IT/Digital, группа специализаций, стрим,
специализация, рекрутер, сорсер, заказчик и его логин, канал, причина и тип поиска,
источники закрытия Jira/Candy, уровни специалиста и финалиста, логин сотрудника, УС-4…6,
тип закрытия, тип HRS). Лимит 10 000 строк, серверной пагинации нет, поиск в таблице.

Датасеты:

| Датасет | Что это |

| `vacancy_daily_virt` | сводная: читает `calc` дважды через `{{dataset(33339)}}`, UNION с итогом и шапкой месяцев, оконные ранги |

Нативные фильтры — 49 и 4 разделителя:

## 2. Почему долго

1. **Открытие — около 50 запросов.** Каждый фильтр-список загружает свои значения
   отдельным запросом, плюс чарт открытой вкладки; «Детализация» — ещё 7. Каскады
   перезапрашивают «Группу специализаций» и «Специализацию» при смене почти любого
   фильтра. Проверить в бою: DevTools → Network → число запросов `chart/data` при открытии.
2. **Список — 240 000 ячеек.** 10 000 строк × 24 колонки записями: на стенде ≈ 24 МБ JSON
   (кириллица в JSON экранируется `\uXXXX`, как по умолчанию делает simplejson Superset;
   без экранирования — 13 МБ), из них почти 10 МБ — имена колонок, повторённые в каждой
   строке. Proteus собирает это на сервере по ячейке, браузер разбирает, стандартная
   таблица держит все 10 000 строк и пересчитывает их на каждую сортировку и букву поиска.
3. **Лишняя работа в запросе:** aggregate с 24 полями GROUP BY вместо сырых строк, HTML
   ссылок собирается в SQL для каждой строки.
4. **Сводная читает источник несколько раз:** `{{dataset(33339)}}` подставлен дважды, а
   ClickHouse 24 переисполняет подзапрос на каждой ссылке.

Сам ClickHouse — не узкое место: на стенде запрос списка — 0,29 с (раздел 7).

## 3. Целевая схема

Как в HRBP HUB: **один чарт на одном датасете на борд**, нативных фильтров нет.

```
prod_proteus.vacancy_daily (≈100 тыс. × 112)
        │  датасет: Jinja читает кросс-фильтры самого чарта (носители в SELECT не выводятся)
        ▼
ответ одним запросом: meta · f (фасеты) · t (деревья КП и УС) · r (строки списка пачками)
        │
        ▼
чарт react_sanbbox: строка фильтров → «Применить» → один запрос;
таблица, страницы, сортировка, поиск, «Копировать» — из памяти, без запросов
```

Строки ответа:

| role | Что | Стенд |
|---|---|---|
| meta | всего строк под фильтрами и всего в таблице, дата данных, эхо фильтров, лимит, сортировка | 1 строка |
| f | для каждого атрибута фильтра — все значения из таблицы (distinct) и число строк при ОСТАЛЬНЫХ фильтрах. Значения с нулём не пропадают, а уходят серым в конец списка — это заменяет каскады | 24 атрибута ≈ 2 600 значений, 0,17 с, 0,3 МБ |
| t | деревья КП и УС окрестностью: 3 верхних уровня, путь до выбранного, дети выбранного, найденное поиском | 3 уровня обоих деревьев — 259 узлов, 0,18 с на дерево |
| r | строки списка пачками по 500: поля через табуляцию, строки через перевод строки; категории — номером значения из `f` | 5 000 строк ≈ 1 МБ |

Носители кросс-фильтра (в SELECT не выводятся, `value = []` не эмитится):

| Носитель | Что несёт |
|---|---|
| `flt_f` | выбранные значения атрибутов парами `атрибут=значение`; атрибут — из белого списка, ≤ 200 значений на атрибут |
| `kp_f`, `us_f` | узлы деревьев (путь именами уровней); строка проходит, если её путь начинается с узла |
| `dt_f` | период закрытия |
| `q_f` | строка поиска: по всему списку (когда он обрезан) и по именам узлов деревьев |
| `sort_f` | колонка и направление (белый список) |
| `lim_f` | 5 000 / 10 000 / 25 000 |
| `cols_f` | колонки сверх набора по умолчанию |

Без носителей датасет отдаёт нынешнее «по умолчанию»: закрытия с 1 января прошлого года,
12 каналов, 5 000 строк, свежие сверху, колонки текущего списка. Лимит строк чарта в
Proteus (10 000) после упаковки считает строки ответа — фасеты, узлы, пачки, — а не
строки списка, поэтому 25 000 строк списка в него помещаются.

Строка фильтров: «Период» (плюс гистограмма месяцев вместо таплок — клик ставит месяц),
«Структура» (два дерева с поиском по имени на любом уровне и путём у находки — как юнит в
HRBP HUB, вместо 21 выпадашки уровней), «Вакансия», «Закрытие и источник», «Рекрутинг». В
каждой группе — списки с поиском и счётчиками. Выбор копится (изменённый — с пунктирной
рамкой) и уходит одним запросом по «Применить · N»; применённое — чипами с ×. Если в
данных это вложенность, «Группа специализаций → Стрим → Специализация», «Группа каналов →
Канал → Детальный источник», «Группа рекрутеров → Рекрутер» показываются деревом, как
структура.

## 4. Лимиты, страницы, сортировка, копирование

| Что | Как |
|---|---|
| По умолчанию | 5 000 строк, по дате закрытия ↓; ответ целиком ≈ 1,4 МБ (строки — 1 МБ) |
| Больше | переключатель «5 000 · 10 000 · 25 000» — тот же один запрос с `lim_f`; 25 000 — 0,67 с в ClickHouse и ≈ 5 МБ ответа |
| Счётчик | «Показано 5 000 из 18 340»: всего считает meta, обрезанный список видно сразу |
| Страницы | по 100 строк из памяти, мгновенно; в DOM — только текущая страница |
| Сортировка | загружено всё (всего ≤ лимита) — в браузере: 25 000 строк сортируются за 30–70 мс. Список обрезан — клик по колонке перезапрашивает первые N уже в этом порядке (`sort_f`), иначе «самые ранние» или «по алфавиту первые» были бы первыми только среди загруженных |
| Поиск | по загруженным — мгновенно (7 мс на 25 000); список обрезан — «искать во всех N» запросом `q_f` |
| Копировать | всё загруженное после поиска и сортировки, видимыми колонками в их порядке (TSV, вставляется в Excel), а не только страница; обрезан — плашка «скопировано 5 000 из 18 340» |
| Больше 25 000 | не в интерактивном борде: сузить фильтры или выгрузка (SQL Lab или отдельная стандартная таблица с экспортом CSV) |

## 5. Что ещё можно (варианты, которые не обсуждали)

1. **Упаковка строк** — главный выигрыш: 240 000 ячеек → ≈ 17 000, имена колонок не
   повторяются в каждой строке.
2. **Словарь категорий.** Значения категорий уже приезжают в фасетах, поэтому в строке
   вместо «Управление персоналом» — номер значения: 5 000 строк — 4,6 → 1,0 МБ, 25 000 —
   23 → 4,9 МБ.
3. **Не везти 112 колонок.** По умолчанию — колонки текущего списка, остальные — в
   «Колонки» (добавленная уходит в `cols_f`, тот же один запрос). По желанию — карточка
   строки со всеми 112 полями по клику, одним маленьким запросом.
4. **Дерево окрестностью и поиск.** Каталог продуктов целиком на стенде — 13,7 тыс. узлов и
   15 МБ ответа, управленческая структура — 7,9 тыс., поэтому как в HRBP HUB: верх
   дерева, путь, дети выбранного и поиск.
5. **Кэш Proteus.** Если запрос по умолчанию не зависит от пользователя (`current_username()`
   нужен только грейду финалиста — отдавать его, только когда колонку добавили), первый
   открывший кладёт ответ в кэш для всех, а после ночного обновления его можно прогреть
   (как параграф «Обновить кеш борда» в HRBP HUB).
6. **Двухступенчатое открытие** — если в бою открытие всё же дольше 2 с: первый ответ —
   фасеты и 1 000 строк (1,3 МБ без словаря), остальное — кнопкой или вдогонку.
7. **Быстрый фикс без своего чарта (вариант 0):** список в raw-режим, серверная пагинация по
   100 строк, ссылки собирать не в SQL, часть фильтров убрать. Снимет 24 МБ, но
   сортировка и поиск станут запросами, копироваться будет только страница, а запросы
   фильтров при открытии останутся.
8. **Предагрегат в GP / Helicopter**, если источник можно менять: узкая таблица списка с id
   узлов КП и УС и кодами категорий, справочник узлов — как `hrbp_hub_unit` в HRBP HUB. На
   100 тыс. строк не обязателен: на стенде всё считается на лету за 0,5 с.

## 6. «Сводная»

Та же строка фильтров и свой датасет агрегатов: «Разрез 1 × Разрез 2», 24 месяца и окна —
одним проходом по источнику, `sumIf` по флагам, которые в таблице уже есть (`ytd`, `pytd`,
`py`, `mtd`, `mtd_y_1`, `last_12_m`, `1_elem…12_elem`, `…_py`), вместо двух чтений `calc` и
UNION. Ответ — сотни строк; «Разрез 1/2» и «Сортировать по» — контролы внутри чарта.

## 7. Замеры стенда

ClickHouse 24.8 (chdb 2.1.1, как в бою), синтетическая `vacancy_daily`: 100 тыс. строк ×
112 колонок той же схемы (Nullable), ≈ 3 % повторов HRS, 400 специализаций, 352 локации,
600 рекрутеров, 800 сорсеров, 8 000 заказчиков, ≈ 3,8 тыс. листьев КП и 3 тыс. УС.
Лучшее из трёх; JSON — как у Superset: записи, кириллица экранирована.

| Запрос | ClickHouse | Строк ответа | JSON | gzip |
|---|---|---|---|---|
| сейчас: список 142653, 24 поля GROUP BY, 10 000 строк | 0,29 с | 10 000 | 24,4 МБ | 1,3 МБ |
| один ответ, без фильтров, 5 000 строк | 0,47 с | 2 895 | 5,0 МБ | 0,36 МБ |
| то же, 1 000 строк | 0,49 с | 2 887 | 1,3 МБ | 0,10 МБ |
| то же, 25 000 строк | 0,67 с | 2 935 | 23,5 МБ | 1,7 МБ |
| то же, 5 000 строк, деревья КП и УС целиком | 0,71 с | 24 285 | 27,9 МБ | 1,3 МБ |
| стрим + узел КП 3-го уровня, 5 000 строк | 0,65 с | 2 886 | 0,6 МБ | 0,04 МБ |
| для сравнения: 5 000 строк × 112 колонок записями | 0,63 с | 5 000 | 33,6 МБ | 2,2 МБ |
| для сравнения: 25 000 строк × 22 колонки записями | 0,24 с | 25 000 | 33,9 МБ | 1,9 МБ |

Плечи ответа по отдельности: фасеты — 0,17 с, дерево — 0,18 с на каждое (3 уровня),
строки — 0,12 с; плечи UNION ALL ClickHouse считает параллельно. Строки со словарём
категорий (оценка перекодировкой ответа): 5 000 — 1,0 МБ вместо 4,6, 25 000 — 4,9 вместо 23.

Браузерная часть (V8, 25 000 строк × 22 колонки): разбор пачек — 44 мс, сортировка по
тексту — 30–70 мс, по дате — 1 мс, поиск — 7 мс (индекс строится один раз за 50 мс), HTML
страницы из 100 строк — меньше 1 мс, TSV для «Копировать» — 33 мс.

Не мерили: накладные Proteus на запрос и разбор ответа сервером — их покажет только бой
(замер «до / после» — вкладка Network).

## 8. Вопросы до сборки

1. **Тот ли отчёт?** В выгрузке «[Найм HQ] Анализ закрытых вакансий», листов «детальные
   списки по Каталогу продуктов» и «по параллельной структуре» нет. Если нужен другой
   дашборд — выгрузить его (Экспорт дашборда → zip) в этот репозиторий.
2. **Какие два борда:** «Сводная» и «Детализация» этого отчёта — или два детальных списка
   (по Каталогу продуктов и по параллельной структуре)?
3. **Строка списка — одна HRS?** Метрики считают `count(distinct issue_full_nm)`, значит, в
   `vacancy_daily` бывают повторы HRS; список сейчас показывает все различающиеся строки.
4. **Колонки по умолчанию** — 24 колонки текущего списка?
5. **Вложенность атрибутов:** группа специализаций → стрим → специализация, группа
   каналов → канал → детальный источник, группа рекрутеров → рекрутер — это дерево в данных?
6. **«Параллельная структура» = управленческая** (`resource_level_*`)? В фильтрах сейчас
   УС-3…11, в разрезах — 2…11.
7. **Чей источник** `vacancy_daily` — можно ли добавить в него колонки (id узлов, коды)?

## 9. План после ответов

По процессу скилла proteus-echarts-builder (репозиторий adoption, ветка `new`):

1. Стенд: синтетика `vacancy_daily` по схеме из выгрузки в chdb 24.8, независимый расчёт
   для сверки (как `stand/` HRBP HUB).
2. Датасет списка: SQL с Jinja, проверки на стенде — старый и новый анализатор,
   `prefer_column_name_to_alias = 1`, `join_use_nulls = 1`, `group_by_use_nulls = 1`,
   враждебный ввод носителей, AlwaysTrue при сохранении датасета.
3. Чарт списка — блоками 1–7, живой стенд поверх chdb.
4. «Сводная» — датасет и чарт.
5. Поставка владельцу: файлы «что куда вставлять» и инструкция, в том числе самовлияние
   кросс-фильтра (сам чарт убрать из `excluded`).
