# Детальные списки — что куда вставлять

Два чарта с одинаковой вёрсткой: **«Детальные списки»** (параллельная структура) и
**«Детальные списки КП»** (каталог продуктов). У каждого свой датасет, и каждый
фильтрует сам себя: все фильтры — внутри чарта, нативные фильтры борда не нужны.
Прежние датасеты и чарты не трогаются — новое заводится рядом, старый борд работает,
пока идёт проба на копии.

| Файл | Куда вставлять |
|---|---|
| `1. Датасет «Детальные списки».sql` | Proteus → новый виртуальный датасет `detail_list`, база CROSS → SQL |
| `2. Датасет «Детальные списки КП».sql` | новый виртуальный датасет `detail_list_kp`, база CROSS → SQL |
| `3. Чарт «Детальные списки».js` | чарт «Детальные списки» (тип ECHARTS) → JS |
| `4. Чарт «Детальные списки КП».js` | чарт «Детальные списки КП» (тип ECHARTS) → JS |
| `5. CSS борда (необязательно).css` | Edit dashboard → CSS, в конец; id чартов вместо `000000` и `111111` |

Файлы 1 и 2 отличаются одной строкой (`MODE`), 3 и 4 — одной строкой (`ns`). Пары не
путать: у каждого чарта свой JS, иначе два чарта на одном дашборде делят состояние.

## Как это работает

- **Открытие — один лёгкий запрос:** итог «N сотрудников» и первые 5 000 сотрудников,
  колонки MasterID и дата найма. Значения фильтров и деревья структур грузятся, когда их
  открывают (≈0,3–1 с), поиск юнита или значения — только найденным.
- **Фильтры копятся** и уходят одной кнопкой «Применить · N» (набранное — пунктиром).
  «Период» (последний день / на дату), «Численность», «Тип ЮЛ», **«Структура»** — один
  выбор вместо уровней: вкладки УС / ЮС / КП, дерево и поиск по названию на любом уровне,
  **«Фильтры»** — 26 атрибутов по группам, у значения — число сотрудников при остальных
  фильтрах (нули серым в конце — вместо каскадов), **«Сотрудники»** — вставка списка
  MasterID, логинов, табельных или Siebel ID.
- **Колонки:** грузятся только показанные. Добавить — одним запросом, убрать — сразу.
  Пресеты «Персоналка», «Рабочие данные», у КП — «КП-разрез».
- **Сортировка:** все сотрудники загружены — сразу; нет — запрос «первые N по этой
  колонке». «Загружать» — 5 000 / 10 000 / 25 000.
- **Без запроса:** страницы, поиск по таблице, группировка (до 3 уровней), перестановка
  и ширина колонок, «Копировать» — все загруженные строки (с учётом поиска) для Excel.
- **Доступ — как раньше:** warden по логину маскирует персональные данные, грейд,
  сеньорность и оценку (в ячейке «⛔ нет доступа», в «Копировать» — прежний текст).
  Логина нет в warden — плашка вместо списка.
- **КП:** строка на аллокацию (блок сотрудника, поля сотрудника — одной ячейкой на блок),
  если показана аллокация или уровень КП; иначе — строка на сотрудника. «Суммарная
  аллокация» и «Кол-во аллокаций» считает чарт.

## 1. Датасеты

1. Proteus → Datasets → новый виртуальный датасет, база **CROSS** (та же, что у
   `mdm_employee_d_detail_echarts`), имя `detail_list`. SQL — файл 1 целиком →
   сохранить. Сохранение исполняет запрос с пустыми фильтрами и вашим логином — секунды.
2. То же — `detail_list_kp`, файл 2.
3. Колонок у каждого 5: `role, k, v, n, j`. Если SQL меняли у уже созданного датасета и
   колонки изменились — «Синхронизировать столбцы».
4. Проверка (необязательно): SQL Lab, база CROSS, файл 1 целиком → Run. Одна строка
   `meta` и десять строк `r` (5 000 сотрудников пачками по 500).

## 2. Копия борда

Копия дашборда 7241 (или новый дашборд) с двумя вкладками — «Детальные списки» и
«Детальные списки КП», на каждой один чарт из п. 3 во всю ширину, высота 1 000–1 400 px
(внутри чарт прокручивается сам). **Нативные фильтры в копии удалите все** — в новых
чартах их заменяет строка фильтров.

## 3. Чарты

Для каждого из двух:

1. Новый чарт на датасете `detail_list` (для КП — `detail_list_kp`), тип **ECHARTS**
   (кастомный JS). Можно взять копию прежнего чарта и сменить датасет.
2. **Измерения** — `role  k  v  n  j`, точными именами, в любом порядке. Мер нет.
   Сортировки нет. **Лимит строк — 50 000** (не меньше 25 000: у КП сейчас стоит 10 000 —
   мало, при открытых фильтрах пропадёт служебная строка meta). Серверная пагинация — выкл.
3. JS — файл 3 (для КП — файл 4) целиком. Сохранить.

## 4. Кросс-фильтр на себя

Без этого «Применить», колонки, сортировка, лимит и загрузка фильтров не работают —
через 30 секунд чарт сам скажет жёлтой плашкой. Мышкой в интерфейсе не настраивается,
правится JSON-метаданными дашборда (так настроен HRBP HUB):

1. **id чартов:** меню чарта «⋮» → «Редактировать график» — число после `slice_id=` в
   адресе. Ниже `ID1` — «Детальные списки», `ID2` — «Детальные списки КП».
2. Дашборд → «…» → «Редактировать свойства» → «Дополнительно» → «JSON метаданные».
3. `"cross_filters_enabled"` → `true` (нет ключа — добавьте строку `"cross_filters_enabled": true,`).
4. Блок `"chart_configuration"` замените целиком (нет — добавьте):
   ```json
   "chart_configuration": {
     "ID1": {
       "id": ID1,
       "crossFilters": {"scope": {"rootPath": ["ROOT_ID"], "excluded": [ID2]}, "chartsInScope": [ID1]}
     },
     "ID2": {
       "id": ID2,
       "crossFilters": {"scope": {"rootPath": ["ROOT_ID"], "excluded": [ID1]}, "chartsInScope": [ID2]}
     }
   },
   ```
   Каждый чарт фильтрует только себя: по умолчанию в `excluded` стоит сам чарт, и свой
   фильтр до него не доходит. В ключах `"ID1"`, `"ID2"` числа в кавычках, в остальных
   местах — без. Если чарт окажется и в области второго — данные не перепутаются (у
   носителей разные имена: `…_f` и `…_kf`), лишь добавятся лишние запросы.
5. Сохранить свойства → «Сохранить» дашборд → обновить страницу.

## 5. CSS (необязательно)

Файл 5 убирает заголовки чартов и поля вокруг (у виджета своя шапка). `000000` → id
чарта «Детальные списки», `111111` → «Детальные списки КП», во всех местах.

## 6. Что проверить на пробе

1. Открытие: «84 875 сотрудников · в таблице первые 5 000 по «MasterID» ↑» (ваше число),
   две колонки, 100 строк на странице. Время открытия — главное, ради чего переделка.
2. «Структура» → «Загружаю структуру…» → дерево; поиск «инвест» — находки с путём.
   Отметить юнит → «Применить · 1» → итог сузился, юнит — в чипе под строкой фильтров.
3. «Фильтры» → «Стрим» → значение → «Применить». Число у значения — сотрудники при
   остальных фильтрах.
4. «Колонки» → «Рабочие данные» → «Показать»: загрузка одним запросом; снять колонку —
   сразу. Клик по заголовку — сортировка; перетащить заголовок — порядок; край — ширина.
5. «Загружать: 25 000», «Копировать» → вставить в Excel: даты ДД.ММ.ГГГГ, стаж с запятой.
6. «Сотрудники» → вставить несколько MasterID → «Применить».
7. То же на вкладке КП: блоки сотрудников, «КП-разрез», дерево КП.
8. Логин без строки в warden — плашка вместо списка; с частичным доступом — «⛔ нет
   доступа» в скрытых полях, как в прежнем чарте.

## 7. Замена на проде

Когда проба прошла:

1. На боевом дашборде у двух чартов — датасет, «Измерения», лимит и JS, как в п. 1–3.
2. JSON-метаданные — как в п. 4, с id боевых чартов (другие записи `chart_configuration`,
   если есть, оставить).
3. Нативные фильтры: у каждого в «Области действия» снимите эти два чарта (фильтры
   нужны другим вкладкам — выгрузкам, трансформеру). Если других вкладок нет — удалите.
4. Прежние датасеты `mdm_employee_d_detail_echarts`, `…_functional_echarts` и
   справочники `cross_filter_*_structure` новым чартам не нужны; удалять — только когда
   ими не пользуется ничто другое.

Откат — вернуть чартам прежние датасет, «Измерения» и JS (прежний JS — в выгрузке
дашборда 7241, ключ `jsx` у чартов 726821 и 795014).

## 8. Если что-то не так

| Симптом | Причина и что сделать |
|---|---|
| Жёлтая плашка «Ответа на запрос нет 30 секунд…» | чарт не фильтрует сам себя — п. 4; если плашка только на тяжёлом запросе (25 000 × много колонок) — запрос ещё идёт |
| «В данных чарта нет колонок: …» | не все 5 полей в «Измерениях» или не синхронизированы столбцы — п. 1.3, 3.2 |
| «Нет служебной строки meta» | мал лимит строк — п. 3.2 |
| «Фильтры не применились: нет applyCrossFilter» | чарт открыт вне дашборда (в редакторе) — там фильтры не работают |
| «Для вашего логина нет строки в таблице доступа warden» | логина нет в `warden_access_array_cross` — как и у прежнего чарта |
| «Структура не загружена. Загрузить» | запрос структуры не прошёл — «Загрузить» повторит его |
| «Показаны первые 900 строк — найдите юнит поиском» | дерево большое: раскрытие узла догружает его подразделения, остальное — поиск |
| Поиск юнита по КП на большом каталоге — 1–3 с | ищет по путям всех аллокаций; уточните слово |
| «Значений в фильтрах — не больше 200 у атрибута и 500 всего» | предел длины запроса ClickHouse; для длинных списков сотрудников — «Сотрудники» (до 2 000) |
| Ошибка ClickHouse о колонке | колонка источника переименована — сверьте с прежним датасетом: новый читает те же колонки |

## 9. Что проверено до поставки

Стенд — синтетика ≈100 тыс. сотрудников (≈200 тыс. строк аллокаций у КП), ClickHouse 24.8
(chdb 2.1.1 — версия боя), репозиторий, папка `stand/`:

- **Датасеты — 292 проверки, 0 провалов** (`stand/check.py`): при тех же фильтрах новый
  отдаёт тех же сотрудников и те же значения всех полей, включая маски warden, что и
  прежний датасет из выгрузки 7241 (4 вида доступа, 17 наборов фильтров на режим);
  значения фильтров, деревья, флаг «есть дети», дети узла, поиск — против независимого
  расчёта; враждебный ввод, сохранение датасета (AlwaysTrue), логин без warden, старый
  анализатор, `prefer_column_name_to_alias`, `join_use_nulls`, `group_by_use_nulls`;
  худший запрос (2 000 логинов + 500 значений) — 194 КБ, меньше `max_query_size`.
- **Чарты — 58 шагов живого прогона, 0 провалов** (`stand/click.cjs`: каждый контрол обоих
  чартов в браузере), smoke скилла proteus-echarts-builder — 0 провалов, ESLint `no-undef` — 0.
- **Скорость** (стенд, один узел; в бою — кластер):

| Действие | Сейчас (прежние чарты) | Новые |
|---|---|---|
| Открытие | 4,4 с ClickHouse + 84 МБ + 9,4 с разбор в браузере | ≈0,3 с запрос, 0,1 МБ, 0,05 с разбор |
| «Применить» (5 000 × 2 колонки) | — | ≈0,3–0,6 с |
| Структура / значения фильтров по открытию | — | 0,3–1 с |
| 25 000 × 20 колонок | — | 1 с запрос, 16 МБ, 0,23 с разбор |
| КП, 25 000 сотрудников × 24 колонки | — | 1,6 с запрос, 28 МБ, 0,37 с разбор |
| Страница, поиск по таблице, сортировка и группировка загруженного, 25 000 строк | сортировка 0,2–0,7 с | 0,02–0,2 с |

## 10. Что стендом не проверено

Боевые объёмы и время ClickHouse-кластера; размер деревьев в бою (УС ≈10 тыс. юнитов —
дерево приходит верхними тремя уровнями, глубже — раскрытием узла и поиском); поведение
двух чартов на соседних вкладках одного дашборда (у них разные `ns` и имена носителей —
состояние и фильтры не пересекаются); DOM борда для CSS (файл 5 необязателен).
